## 问题 1：`sync_from_seoul.sh` 100% 空转

### 1.1 现场证据

小五 `~/go/sync_from_seoul.sh`：

```bash
12 # 检查源文件新鲜度
13 FRESH=$(ssh -o ConnectTimeout=5 seoul "find $SRC_PATH -mmin -120 2>/dev/null | wc -l" ...)
14 if [ "$FRESH" -eq 0 ]; then
15     echo "... ⚠️ 首尔文件超过120分钟未更新，跳过" >> "$LOG_PATH"; exit 0
17 fi
```

日志统计（`/tmp/seoul_sync.log`，起点 2026-05-20）：

- `跳过` 117 次
- `同步完成` **0 次**
- 首条即失败：`2026-05-20 19:48:17 ⚠️ 首尔文件超过120分钟未更新，跳过`
- 最近 15 个交易日（10-19 → 11-06）连续失败

### 1.2 根因（两层，第二层才是致命的）

1. **时区差 1 小时**：首尔 KST(+9) 写库 `18:11`，小五 CST(+8) 的 02:00 = 首尔 03:00，实际间隔 **8h49m ≈ 529 分钟 ≫ 120 分钟**。判断条件恒为「不新鲜」。
2. **判断语义错误（更根本）**：`-mmin -120` 问的是「这个文件在过去 2 小时内是否被写过」。而这个任务本来就是**每天只跑一次、要求同步昨天的收盘库**，间隔天然 8 小时以上。**只要不改判断维度，窗口调到多大都只是掩盖问题**：
   - 调到 `-1440`（24h）：工作日能过，但**周一 02:00 距上周五 18:11 已 56 小时**，周一必跳过；遇到周一节假日更糟。
   - 结论：mtime 只能在「同一次写入窗口内」做有效性判断，不能用作日常同步闸门。

### 1.3 两种改法对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 放宽窗口到 1440 | `find -mmin -1440` | 改 1 个字符 | 周一/节后必漏；仍然不知道「到底同步没同步」；源库若 3 天没更新也会照抄 | ❌ 不采纳 |
| B. 比 `max(date)` | 分别查两端 `stock_prices` 的 `max(date)`，远端 > 本地才同步 | 语义精确、周末/节假日天然正确、可幂等重跑、能自证「已同步」 | 多两次 DuckDB 查询（各 ~0.1s，read_only 无锁风险） | ✅ **推荐** |

B 的严谨做法是「远端 max(date) > 本地 max(date) 才同步；相等则明确记录 ✅ 已是最新」，并**保留**一次 mtime 检查作为辅助告警（远端库超过 3 天没更新 → 记 WARN，说明首尔采集链路本身有问题）。

### 1.4 具体改法（替换第 12–20 行）

```bash
#!/bin/bash
# 上海小五 ← 首尔 同步日线数据库
set -euo pipefail
SRC_PATH='/home/ubuntu/go/data/stock_data.duckdb'
DST_PATH='/home/ubuntu/go/data/stock_data.duckdb'
TMP_PATH="${DST_PATH}.tmp"
LOG_PATH='/tmp/seoul_sync.log'
log(){ echo "$(date '+%F %T') $*" >> "$LOG_PATH"; }

log "开始从首尔同步..."

q_max_date() {          # $1=远端host(空=本地) $2=db路径
  local py="import duckdb;c=duckdb.connect('$2',read_only=True);print(c.execute('select max(date) from stock_prices').fetchone()[0])"
  if [ -n "$1" ]; then
    ssh -o ConnectTimeout=8 -o BatchMode=yes "$1" "python3 -c \"$py\"" 2>/dev/null
  else
    python3 -c "$py" 2>/dev/null
  fi
}

SRC_MAX=$(q_max_date seoul "$SRC_PATH" || true)
LOCAL_MAX=$(q_max_date "" "$DST_PATH" || true)

if [ -z "$SRC_MAX" ]; then
  log "❌ 无法读取首尔 max(date)（可能正在写入/无 duckdb），跳过"
  exit 1
fi
if [ -n "$LOCAL_MAX" ] && [[ ! "$LOCAL_MAX" < "$SRC_MAX" ]]; then   # ISO 日期串可直接比较
  log "✅ 已是最新 (local=$LOCAL_MAX remote=$SRC_MAX)，跳过"
  # 辅助告警：远端超过 72h 未更新，说明首尔采集链路有问题
  FRESH=$(ssh -o ConnectTimeout=5 seoul "find $SRC_PATH -mmin -4320 | wc -l" 2>/dev/null || echo 1)
  [ "$FRESH" -eq 0 ] && log "⚠️ 首尔库已超过 72h 未更新，请检查首尔 daily_collect"
  exit 0
fi
log "需要同步: local=${LOCAL_MAX:-NONE} -> remote=$SRC_MAX"
```

**关键纠正**：小五的 latest date 是 **11-06**，与小五本地文件 mtime（11-06 16:40）一致 —— 它并没有停在「比首尔晚一天」，因为 Mac 侧 `daily_collect_push.sh`（工作日 16:15）→ `collect_and_push.py` → `push_incremental("xiaowu", ...)` 一直在给小五补最新数据。**02:00 的首尔同步线是一条从未生效的「冗余链路」**，所以问题 1 才长期没人发现。

### 2.2 缺失日期清单（首尔有、小五完全为 0）

```
2026-06-08 06-09 06-10 06-16 06-22 06-23 06-24 06-25 06-26 06-29 06-30
2026-07-03 07-09 07-10 07-13 07-14 07-15 07-16 07-17
2026-09-01
2026-10-08 10-09 10-14 10-15 10-16 10-23
```

共 26 天，合计 131,878 行。已抽查确认 **Mac 主库里有这些日期**（`2026-10-15` 5,215 行、`2026-07-14` 5,196 行），首尔也有，**只有小五缺** → 属于 `mac_to_xiaowu_sync.py` / `collect_and_push.py` 增量推送漏推，而不是采集端缺数据。

漏推呈「成段」分布（6 月 13 天连成一片、10 月 7 天连成一片），典型特征是**推送按「最近 N 天」回溯**：一旦某天推送失败、后面几天又只回看最近几天，中间那段就永久成为空洞。修完同步线后必须**按日期补齐**，否则永远补不上。

240MB 的构成（供参考，不必强求对齐）：
- 13 张 `stock_sectors_bak_YYYYMMDD`（每张 70,259 行）≈ 主要部分；
- 131,878 行 `stock_prices` + 160 行 `index_prices` + 57 行 `exp_trade`；
- DuckDB 的块分配/空闲页差异（两边不是同一次 CHECKPOINT 产物，体积不会严格相等）。

## 问题 3：403 的真因是「分组被删」，不是 key 过期/额度不足

### 3.1 实测（在小五上直连，未打印 key 明文）

```
GET  /v1/models            → HTTP 403
{"code":"GROUP_DELETED","message":"API Key 所属分组已删除"}
POST /v1/chat/completions  → HTTP 403  同一错误体
不带 Authorization         → HTTP 401 {"code":"API_KEY_REQUIRED", ...}
```

关键判断：
- 无 key 是 **401 `API_KEY_REQUIRED`**，说明服务端能正常解析鉴权头；
- 带 key 是 **403 `GROUP_DELETED`**，说明 **key 已被识别**（不是拼写错、不是被截断——实测长度 67，前缀 `sk-137`、后缀 `3447`，与文件内一致，无省略号）；
- 因此：**api.schyler.top 是 one-api/new-api 类中转站，管理员把该 key 所属「分组」删除了**。这类错误换 base_url 无效、重试无效、改模型无效，属于**永久性失效**。

顺带排查：小五上没有任何备用 key（`~/go/.env`、`~/.bashrc`、`~/.profile` 中均无 DEEPSEEK/OPENAI/SCHYLER 等 `sk-` 变量），所以「降级到另一个 key」目前不可行。

### 3.2 方案（按推荐顺序）

**方案 A（立即可做，零依赖）：本地规则摘要，AI 变可选**
巡检本质是「一句话播报」，把判断逻辑写死比调模型更可靠、更快、不花钱，也不会再 403。

```python
# 替换 xiaowu_check.py 的 analyze()，并新增 rule_summary()
import os
API_KEY = os.getenv("XW_AI_KEY", "")          # 不再硬编码
API_BASE = os.getenv("XW_AI_BASE", "https://api.schyler.top/v1")
MODEL = os.getenv("XW_AI_MODEL", "gpt-5.5")

def rule_summary(results):
    bad = []
    if results.get("seoul_ssh") != "OK":        bad.append("首尔SSH断")
    if str(results.get("seoul_snap","")).startswith("⏰"): bad.append("首尔快照滞后")
    if results.get("seoul_snap") in ("NODATA","PARSE"):    bad.append("首尔快照无数据")
    for k, label in (("xw_oc","小五OC"),("xw_db","小五DB")):
        v = str(results.get(k,""))
        if v in ("DOWN","NODATA") or v.startswith("ERR"): bad.append(f"{label}异常")
    if results.get("xw_disk","").endswith("%") and int(results["xw_disk"].split("(")[-1].rstrip("%)") or 0) >= 85:
        bad.append("小五磁盘≥85%")
    return "；".join(bad) if bad else "各服务正常"

def analyze(now_str, results):
    summary = rule_summary(results)
    if not API_KEY:
        return summary                      # 无 key 直接走规则，不再每轮 403
    try:
        import requests
        r = requests.post(f"{API_BASE}/chat/completions",
            headers={"Authorization": f"Bearer {API_KEY}"},
            json={"model": MODEL, "messages": [{"role": "user", "content": prompt}], "max_tokens": 80},
            timeout=(3, 10))
        if r.status_code == 200:
            return r.json()["choices"][0]["message"]["content"].strip()
        if r.status_code in (401, 403):      # 永久失效：本次进程内禁用，避免刷屏
            globals()["API_KEY"] = ""
            return f"{summary}（AI 鉴权失败 {r.status_code}，已降级）"
        return summary
    except Exception:
        return summary
```

**方案 B（要 AI 就换 key）**：登录 api.schyler.top 控制台 → 新建一个**归属仍存在的分组**的令牌 → 写到小五 `~/go/.env`（`chmod 600`，`XW_AI_KEY=...`），脚本用 `os.getenv` 读取（方案 A 的骨架已支持）。换完先验证：

```bash

  -H "Authorization: Bearer $XW_AI_KEY" https://api.schyler.top/v1/models   # 期望 200
```

**方案 C（不想依赖中转站）**：改用官方 DeepSeek（`https://api.deepseek.com/v1`，`deepseek-chat`），需要单独申请 key；小五没有 GPU，不适合本地推理。

### 3.3 附带问题

- `report()` 的 `alert` 判定列表是 `["DOWN","ERR","NODATA","⏰"]`，**不包含 `API:`**，所以 403 只显示「🧠 API:403」，不会置 ⚠️。建议把 AI 层失败降级为信息项、但连续失败 N 次时提示一次。
- 每半小时一次的外呼会持续写 403 日志；方案 A 的 `globals()["API_KEY"]=""` 可止血。

## 问题 4：14:00 的 STALE 是**误报**，接收端从未掉线

### 4.1 反证链（三条独立证据）

1. **告警时刻高度规律**：`/tmp/snapshot_health.log` 里所有 STALE 都是 `14:00:0x`，`12:00`/`12:30`/`13:30`/`14:30` **一条都没有**。11-04、11-05、11-06 每天各只有 1 条：

```
2026-11-05 14:00:01 STALE {... "last_snapshot":"2026-11-05T11:31:00","stale_minutes":89,"in_session":true ...}
2026-11-06 14:00:02 STALE {... "last_snapshot":"2026-11-06T11:30:51","stale_minutes":89 ...}
```

2. **30 分钟后自动恢复，且期间没有任何重启动作**：`snapshot_health.sh` 的 STALE 分支**只记日志、不重启**（第 20 行），14:00–14:30 之间日志里也没有 `API_DOWN`。既然 14:30 不再报陈旧，说明 **14:00–14:30 之间有新快照写入** —— 数据面自己恢复了。

3. **时间换算**：首尔是 `Asia/Seoul +0900`（`timedatectl` 已确认），A 股时段换算过去是 **10:15–12:30 / 14:00–16:05**。所以：
   - 最后一条早盘快照 = `12:30:51 KST`（`/health` 展示为 `11:30:51` CST，代码里 `last - 1h` 的换算是对的）；
   - 告警发生在 `14:00 KST` = **北京 13:00 整**，正是下午开盘第一分钟；
   - `stale_minutes = 89` **就是午休时长**（11:30→13:00），不是故障时长。

4. **旁证**：`snapshots` 库最后一次写入是 `2026-11-06 16:05:51 KST` = 北京 15:05，正是 `snapshot_loop.sh` 的 `AFTER_END=15:05` —— 说明发送侧整个下午都在正常推送（若 13:00 没恢复，15:05 那次写入也无从谈起）。本机盘中库 `intraday_snapshots_2026-11-06.duckdb` 里 `13h` 有 60 个分钟点、20 万行，也证明源数据下午齐备。

### 4.2 为什么「restart 就恢复」

因果倒置。restart 恰好发生在 14:0x，而新快照本来就在 13:00:30 左右到达；你看到的下一次 14:30 检查当然就正常了。**不 restart 也会恢复**（14:00–14:30 之间无任何 API_DOWN/DB_LOCKED 记录就是证据）。真正被这习惯掩盖的风险是：**交易时段内重启 API，会让单线程服务直接断开所有在用连接**，反而制造真实抖动。

### 4.3 修复：让新鲜度判断感知「午休/开盘」

`snapshot_api.py` 现状（第 76–88 行）用 `now_local - last` 直接当陈旧度，交易时段 >30 分钟即 `ok=false`。改为**以「本场开盘时刻」为锚**：午休前的旧快照在开盘初期不算陈旧，只有「开盘已过 N 分钟而仍无新数据」才算。

```python
def session_open_cst(now_cst):
    """返回当前交易时段的开盘锚点（北京时间）；非交易时段返回 None"""
    if now_cst.weekday() >= 5:
        return None
    m = now_cst.hour * 60 + now_cst.minute
    if 9 * 60 + 15 <= m <= 11 * 60 + 30:
        return now_cst.replace(hour=9, minute=25, second=0, microsecond=0)   # 集合竞价后首笔
    if 13 * 60 <= m <= 15 * 60 + 5:
        return now_cst.replace(hour=13, minute=0, second=0, microsecond=0)
    return None


def freshness():
    """返回 (ok, last_snapshot_str, stale_minutes, in_session, rows, err)"""
    try:
        c = connect_ro()
        try:
            last, rows = c.execute('SELECT MAX(created_at), COUNT(*) FROM snapshots').fetchone()
        finally:
            c.close()
    except Exception as e:
        return False, None, None, in_trading_session(datetime.now(CST)), 0, str(e)

    if last is None:
        return False, None, None, in_trading_session(datetime.now(CST)), 0, None

    now_cst    = datetime.now(CST)
    last_cst   = last - timedelta(hours=1)          # KST -> CST
    sess       = in_trading_session(now_cst)
    age_min    = int((now_cst - last_cst).total_seconds() // 60)

    anchor = last_cst
    if sess:
        op = session_open_cst(now_cst)
        if op and last_cst < op:
            anchor = op                              # 午休/开盘前的快照不参与陈旧判定
    stale_min = int((now_cst - anchor).total_seconds() // 60)

    ok = stale_min <= STALE_LIMIT_MIN if sess else (age_min <= 4 * 24 * 60)
    return ok, last_cst.strftime('%Y-%m-%dT%H:%M:%S'), stale_min, sess, rows, None
```

效果：`14:00 KST` → `stale_min=0`（不再误报）；`14:35 KST` 仍无新数据 → `stale_min=35` → 如实报警。建议 `/health` 同时返回 `age_minutes`（原始年龄）便于排障，`stale_minutes` 改为「开盘后无新数据时长」。

### 4.4 同时修两个真实缺陷

**(a) API 随机 `API_DOWN`（每天 1–2 次，时间不定：03:00 / 18:00 / 23:30…）**
`snapshot_api.py` 第 95 行用的是 `http.server.HTTPServer` —— **单线程**，`BaseHTTPRequestHandler.timeout` 默认 `None`。任何半开连接（客户端异常断连，日志里成片的 `ConnectionResetError` 就是证据）都能把 accept 循环卡住，导致 `/health` 5 秒超时 → 被 health 脚本 `systemctl restart`。

```python
# 1) Handler 增加读超时
class Handler(http.server.BaseHTTPRequestHandler):
    timeout = 10

# 2) 主入口改为多线程
if __name__ == '__main__':
    print(f'Snap API http://0.0.0.0:{PORT}')
    srv = http.server.ThreadingHTTPServer(('0.0.0.0', PORT), Handler)
    srv.daemon_threads = True
    srv.serve_forever()
```

> 注意：`_json()` 没写 `Content-Length`，所以**不要**顺手打开 `protocol_version = 'HTTP/1.1'`（会变成 keep-alive 挂起）。保持 HTTP/1.0 + 多线程即可。

**(b) 健康检查时点与频率**
`*/30 * * * *` 恰好把探测点钉在整点/半点 —— 13:00 这个「必然陈旧」的时刻被反复命中。即使不做 (4.3) 的代码修复，也应避开开盘边界：

```cron
# 原: */30 * * * *
*/5 9-15 * * 1-5 /home/ubuntu/go/snapshot_health.sh >> /tmp/snapshot_health.log 2>&1
0 * * * *        /home/ubuntu/go/snapshot_health.sh >> /tmp/snapshot_health.log 2>&1
```

并加「状态变化才写日志」去重，避免 STALE 期间每 5 分钟刷一行：

```bash
STATE=$(echo "$FRESH" | python3 -c 'import sys,json;d=json.load(sys.stdin);print("STALE" if not d.get("ok") else "OK")' 2>/dev/null)
[ "$STATE" != "$(cat /tmp/snapshot_health.state 2>/dev/null)" ] && { echo "$TS $STATE $FRESH" >> $LOG; echo "$STATE" > /tmp/snapshot_health.state; }
```

**(c) 可选：接收端心跳**
发送端每次成功写入后 `touch /tmp/snapshot_last_push`；health 脚本检查该文件 mtime。这样能把「发送端挂了」与「行情源没数据」区分开，而不是靠 `created_at` 猜。
